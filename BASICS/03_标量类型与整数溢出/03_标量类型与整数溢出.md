# 第 03 课 · 标量类型与整数溢出

> 所需工具链：rustc 1.85+（edition 2024） ｜ 讲解：本文件 ｜ 独立代码：`03_scalars_and_overflow.rs`

## 一、底层原理

### 1.1 标量类型的布局与取值范围

Rust 的标量类型大小是**规范固定的**（`usize`/`isize` 除外），不是"编译器爱怎么排就怎么排"：

| 类型 | 字节 | 取值范围 / 表示 |
|---|---|---|
| `i8` / `i16` / `i32` / `i64` / `i128` | 1 / 2 / 4 / 8 / 16 | `-2^(n-1) ..= 2^(n-1)-1`，二进制补码 |
| `u8` / `u16` / `u32` / `u64` / `u128` | 1 / 2 / 4 / 8 / 16 | `0 ..= 2^n-1` |
| `isize` / `usize` | 指针宽度（x86_64 上 8） | 有符号 / 无符号的指针大小整数 |
| `f32` / `f64` | 4 / 8 | IEEE 754 binary32 / binary64 |
| `bool` | 1 | 只有 `0` 和 `1` 两个有效值 |
| `char` | 4 | Unicode 标量值 `0..=0x10FFFF`，不含代理区 |

两个容易忽略的点：

- **整数没有"无效位模式"**：任意 8 位都是合法的 `u8`，任意 `i8` 也合法。
  所以整数的 `transmute`/位运算永远是定义良好的；浮点则有 `NaN` 和 `±inf` 这些特殊值。
- **`usize` 不是 `u64` 的别名**：它只保证"和指针一样宽"。32 位目标上它是 4 字节，
  跨平台代码里把 `u64` 直接 `as usize` 可能截断。索引、长度、容量用 `usize`，
  文件大小、时间戳、协议字段用定宽整数（`u64`/`u32`）。

### 1.2 补码：同一串比特，两种解释

`i8` 的 `-1` 在内存里就是 `0xFF`；把它当 `u8` 读就是 `255`。`as` 在整数之间
**不改变位模式**，只改变"怎么解释这些位"：

```rust
(-1i8) as u8   // 255：符号位变成最高数值位
(255u8) as i8  // -1：反过来解释
300u16 as u8   // 44：只保留低 8 位（300 mod 256）
```

因此 `as` 是"位级重解释"，不是"数值转换"：它**从不检查、从不 panic、也从不报错**。
需要"值不变"的转换时应当用 `From`/`TryFrom`（第 17 课），让编译器帮你检查范围。

### 1.3 整数溢出：编译期、debug、release 三层语义

这是 Rust 与 C/C++ 差异最大、也最容易被误解的地方。同一句 `a + b`，行为取决于**三个层次**：

| 层次 | 触发条件 | 行为 |
|---|---|---|
| 编译期 | 编译器能在编译期算出结果且溢出 | **编译错误**：`arithmetic_overflow`（deny-by-default） |
| debug 构建 | 默认 `debug-assertions` 开启 → `overflow-checks` 开启 | 运行时 **panic**：`attempt to add with overflow` |
| release 构建 | `-O` 默认关闭检查 | 按二进制补码**回绕**（模 `2^n`） |

```rust
let x: u8 = 255 + 1;      // 编译错误：常量表达式溢出
let mut y = 255u8;        // 运行期才确定
y += 1;                   // debug: panic；release: y 变成 0
```

编译选项可以直接改写后两层：

```bash
rustc -O -C overflow-checks=on  app.rs   # release 也保留溢出检查（推荐给安全敏感程序）
rustc -C debug-assertions=off   app.rs   # debug 关闭断言（不推荐）
```

为什么 Rust 要分两套语义？因为两个目标本来就冲突：

- **开发期**要尽早暴露 bug → debug 用 panic 把溢出变成显式错误
- **发布期**要可预测的性能，且某些算法（哈希、校验和、加密）本来就依赖回绕
  → release 用补码回绕，并把这些场景统一收敛到 `wrapping_*` 上显式表达

与 C/C++ 的对比：

| 语言/场景 | 有符号溢出 | 无符号溢出 |
|---|---|---|
| C/C++ | **未定义行为**（优化器可以假设不会发生） | 定义为回绕 |
| Rust debug | panic（定义良好） | panic（定义良好） |
| Rust release | 回绕（定义良好） | 回绕（定义良好） |

Rust 没有任何一种"溢出 UB"——最坏情况是 panic 或回绕，都是语言规范规定的。
但"定义良好"不等于"正确"：release 下的静默回绕仍然是线上事故的常见来源。

### 1.4 除法：两个永远检查的特例

整数除法/取余有两个必须特殊处理的情况，它们**在所有编译模式下都 panic**，
因为 LLVM 的 `sdiv`/`srem` 在这些输入上是未定义行为，rustc 必须提前拦截：

| 运算 | 行为 |
|---|---|
| `x / 0`、`x % 0` | panic（debug 与 release 都是） |
| `i32::MIN / -1`、`i32::MIN % -1` | panic（数学结果超出范围） |

其余 `+ - *` 才遵循 1.3 的"debug panic / release 回绕"。
想避免 panic 就用 `checked_div` / `checked_rem`，它们在上述两种情况都返回 `None`：

```rust
i32::MIN.checked_div(-1)   // None
7u8.checked_div(0)         // None
```

浮点除法则完全不 panic：`1.0 / 0.0` 是 `inf`，`0.0 / 0.0` 是 `NaN`，
`-1.0 / 0.0` 是 `-inf`。

### 1.5 浮点数：IEEE 754 的"不精确"是规范的一部分

`f64` 有 53 位有效位（约 15–17 位十进制），`f32` 只有 24 位（约 7 位）。
`0.1` 在二进制里是无限循环小数，存进去就已经近似了，于是：

```rust
0.1 + 0.2 == 0.3          // false（实际是 0.30000000000000004）
```

更麻烦的是特殊值：

- `NaN != NaN` 恒为 `true`（IEEE 754 规定 NaN 与任何值比较都不相等，包括自己）
- `f64` 只实现 `PartialEq`/`PartialOrd`，**没有 `Eq`/`Ord`**，因此不能直接作为
  `BTreeMap` 的键；排序要用 `total_cmp` 构造全序
- `-0.0 == 0.0` 为 `true`，但两者的位模式不同，`1.0 / -0.0` 是 `-inf`
- `inf - inf`、`0.0 * inf` 都是 `NaN`

所以"浮点相等"必须靠容差判断（相对/绝对 epsilon），而不是 `==`；
金额、计数、ID 这类要求精确的数值，从一开始就应当用整数。

### 1.6 `char` 与 `bool`：不是"小整数"

```rust
size_of::<char>()   // 4：Unicode 标量值，不是 UTF-8 字节
size_of::<bool>()   // 1：只有两个有效值
```

- `char` 存的是 **Unicode 标量值**（`U+0000..=U+10FFFF`，不含 `U+D800..=U+DFFF` 代理区）。
  因此 `'中' as u32 == 0x4E2D`，而 `char::from_u32(0xD800)` 返回 `None`。
- 一个 `char` 在 UTF-8 字符串里可能占 1–4 个字节；`char` 的 4 字节与
  `String` 的字节数**不是同一个维度**（第 10 课展开）。
- `bool` 与整数之间**没有隐式转换**：`if x + 1` 之类的写法不存在；需要显式
  `u8::from(b)` 或 `b as u8`（得到 0/1）。反向 `1 as bool` 则根本不允许。

## 二、具体语法

### 2.1 字面量、后缀与类型推断

```rust
let a = 42;              // 默认 i32
let b = 0xFF_FFu16;      // 下划线分隔 + 十六进制 + 后缀
let c = 0b1010_1010;     // 二进制
let d = 0o755;           // 八进制
let e = 1_000_000i64;    // 十进制
let f = b'A';            // u8 字节字面量，值是 65
let g = 'A';             // char，不是 u8
let h = 1.5;             // 默认 f64
let i = 1.5f32;          // 显式 f32
```

规则细则：

- 整数字面量默认 `i32`，浮点字面量默认 `f64`；上下文可以改变推断结果
  （`let x: u8 = 1;` 里 `1` 就是 `u8`）
- 后缀与目标类型必须一致：`let x: u8 = 300;` 是编译错误"literal out of range"
- **没有隐式数值转换**：`1u8 + 1u16`、`let x: i64 = 1i32;` 都直接报类型错误，
  要么统一类型，要么显式 `as`/`From`
- 整数与浮点之间也不能隐式转换：`1 + 1.0` 编译错误

### 2.2 四种显式的溢出策略

每种整数类型都提供五组方法：普通运算、`checked_*`、`wrapping_*`、
`saturating_*`、`overflowing_*`：

| API | 溢出时 | 返回类型 | 典型场景 |
|---|---|---|---|
| `a + b` | debug panic / release 回绕 | `T` | 已证明不会溢出的热路径 |
| `a.checked_add(b)` | 返回 `None` | `Option<T>` | 不可信输入、必须处理失败 |
| `a.wrapping_add(b)` | 回绕（debug 也不 panic） | `T` | 哈希、校验和、加密 |
| `a.saturating_add(b)` | 钳位到 `MIN`/`MAX` | `T` | 计数器、评分、音量、限流 |
| `a.overflowing_add(b)` | 回绕 + 溢出标志 | `(T, bool)` | 需要同时知道值与是否溢出 |

```rust
u8::MAX.checked_add(1)      // None
u8::MAX.wrapping_add(1)     // 0（debug 下也是如此，不会 panic）
u8::MAX.saturating_add(1)   // 255
u8::MAX.overflowing_add(1)  // (0, true)
```

同一套方法覆盖 `add` / `sub` / `mul` / `div` / `rem` / `neg` / `abs` / `pow` /
`shl` / `shr`；移位超过位宽时 `checked_shl` 返回 `None`，普通 `<<` 会 panic
（debug）或做掩码（release 的移位规则按平台对位宽取模）。

### 2.3 `as` 的转换规则

| 源 → 目标 | 规则 | 例子 |
|---|---|---|
| 整数 → 整数 | 截断/符号扩展低位，模 `2^n` | `300u16 as u8` = `44` |
| 整数 → 浮点 | 就近舍入，可能丢精度 | `16_777_217u32 as f32` = `16_777_216.0` |
| 浮点 → 整数 | 向零取整；`NaN` → `0`；越界饱和（1.45+） | `3.99`→`3`，`1e30`→`i32::MAX` |
| `char` → 整数 | Unicode 标量值 | `'A' as u32` = `65` |
| `u8` → `char` | 直接映射（唯一允许的整数→`char`） | `65u8 as char` = `'A'` |
| `char` → `u8` | 截断低位（不推荐） | `'中' as u8` = `45` |
| `bool` → 整数 | `0`/`1` | `true as u8` = `1` |
| 整数 → `bool` | **不允许** | 编译错误 |

记住一句话：**`as` 只做位级/饱和的机械转换，从不检查语义**。
工程代码里优先用 `From`/`TryFrom`（第 17 课），只在位操作、FFI、
哈希这类"我就是要这些位"的地方用 `as`。

### 2.4 整数除法与取模的方向

```rust
-7 / 2    // -3（向零取整，不是向下取整）
-7 % 2    // -1（余数符号跟随被除数）
7 / -2    // -3
7 % -2    // 1
```

Python 的 `//` 是向下取整，Rust/C 是向零取整——从 Python 转过来最容易在这里踩坑。
需要"数学意义上的模"时用 `rem_euclid`：

```rust
-7i32.rem_euclid(2)   // 1
```

### 2.5 浮点比较与排序

```rust
let a = 0.1_f64 + 0.2_f64;
a == 0.3                       // false
f64::NAN == f64::NAN           // false
f64::NAN.partial_cmp(&0.0)     // None
f64::NAN.total_cmp(&0.0)       // 全序，可用于 sort
(-0.0_f64).to_bits() != 0.0_f64.to_bits()   // true
```

- 判断"近似相等"：`(a - b).abs() < f64::EPSILON` 只在 1.0 附近可靠，
  一般用相对误差 `(a - b).abs() <= tolerance * a.abs().max(b.abs())`
- 排序/去重/做键：用 `total_cmp`（1.62+），它把 `-0.0 < 0.0`、`NaN` 排在两端，
  给出与 `f64::to_bits` 一致的全序
- 需要精确十进制（金额、税率）：用整数最小单位，或 `rust_decimal`/`bigdecimal` crate

## 三、实际应用与最佳实践

### 3.1 场景：不可信输入用 `checked_*`

```rust
fn add_item(current: u8, delta: u8) -> Option<u8> {
    current.checked_add(delta)
}
```

解析配置、处理网络报文、累加用户输入时，"溢出"是**必须处理的业务分支**，
不是"不该发生的 bug"。`?`、`unwrap_or`、`match` 都能自然地接住 `None`。

### 3.2 场景：计数/评分用 `saturating_*`

```rust
let mut score = 250u8;
score = score.saturating_add(10);   // 255
score = score.saturating_add(10);   // 仍是 255
```

"到顶就停"是业务语义（经验值、音量、库存扣减到 0 为止），
`saturating_*` 把它写成类型层面的事实，而不是散落的 `if` 判断。

### 3.3 场景：哈希/校验和必须用 `wrapping_*`

```rust
fn checksum(bytes: &[u8]) -> u32 {
    let mut hash = 0x811c_9dc5u32;
    for &byte in bytes {
        hash ^= u32::from(byte);
        hash = hash.wrapping_mul(0x0100_0193);
    }
    hash
}
```

回绕是 FNV/CRC/哈希算法**定义的一部分**。如果这里写 `hash * prime`，
debug 构建会随机 panic、release 构建才"看起来正常"——这正是
"debug 能跑、release 出错"反过来的经典事故。显式 `wrapping_*` 让两种构建一致。

### 3.4 场景：金额用整数最小单位

```rust
let price_cents = 1999i64;
let total = price_cents.checked_mul(3).unwrap();   // 5997
println!("{}.{:02}", total / 100, total % 100);    // 59.97
```

`f64` 表示不了 0.1，账本上滚几次就会差几分钱。用 `i64` 存"分"是后端最常用的方案；
需要小数位更多（汇率、利率）时用 `rust_decimal` 之类的十进制定点库，
而不是"用 f64 然后四舍五入"。

### 3.5 场景：`usize` 的跨平台边界

```rust
let len = 5usize;
let as_u64 = len as u64;          // 总是安全的
let back = u64::try_from(len).ok();   // 反向要检查
```

- 32 位目标上 `usize` 只有 4 字节，`u64 as usize` 可能截断
- 文件大小、偏移、协议长度用 `u64`，只在"和内存/切片交互"的边界转成 `usize`，
  并用 `try_from` 处理放不下的情况

### 3.6 最佳实践清单

1. **默认类型**：普通整数用 `i32`，需要更大范围用 `i64`，索引/长度用 `usize`
2. **不确定就 `checked_*`**：把"溢出"放进类型系统（`Option`/`Result`），别依赖 debug panic
3. **热路径才用裸 `+`**：并且要能证明不会溢出；release 下出错的代价远高于一次检查
4. **哈希/校验和用 `wrapping_*`**：显式表达"回绕是算法语义"
5. **计数/评分/限流用 `saturating_*`**：钳位比回绕更符合业务直觉
6. **金额/精确小数用整数最小单位或定点库**，永远不要用 `f64`
7. **浮点比较用容差或 `total_cmp`**，不要 `==`；给浮点排序必须处理 `NaN`
8. **`as` 只用于位级转换**；数值转换优先 `From`/`TryFrom`
9. **跨平台代码别假设 `usize == u64`**；定宽类型留给协议与持久化
10. **不要用 `#[allow(arithmetic_overflow)]` 压常量溢出**——那是编译期就能发现的错误

## 常见陷阱

1. **以为 release 也会 panic**：`-O` 下加减乘溢出会静默回绕，线上数据凭空变负/归零。
   要么用 `checked_*`，要么显式开 `-C overflow-checks=on`
2. **以为 debug 的 panic 能保证正确性**：debug 只覆盖跑到的路径，分支没测到照样漏
3. **`300u16 as u8` 以为会报错**：实际是 `44`，`as` 从不检查
4. **`-1i32 as u32` 以为是 1**：实际是 `4294967295`
5. **`as` 丢精度**：`u64` 超过 2^53 转 `f64` 会丢低位；`f64` 转 `i64` 越界会饱和到边界
6. **除零只在 debug panic**：错——整数除零与 `MIN / -1` 两个模式都 panic
7. **`i32::MIN / -1` 在 release 回绕**：错——它会 panic（LLVM 层面否则是 UB）
8. **浮点 `==` 判等**：`0.1 + 0.2 != 0.3`；`NaN` 连自己都不等于自己
9. **`-0.0 == 0.0` 为 true，但位模式不同**：哈希、序列化、`to_bits` 比较时会露馅
10. **把 `char` 当字节**：`'中'` 是 4 字节的 `char`、3 字节的 UTF-8，`'中' as u8` 得到 `45`
    这种无意义的值
11. **常量表达式溢出当运行期处理**：`let x: u8 = 255 + 1;` 是编译错误，不是 panic
12. **`usize as u32` 在 64 位机上截断**：长度超过 4G 时静默丢高位
13. **`abs()` 在 `MIN` 上 panic**：`i32::MIN.abs()` 在 debug 下溢出，要用 `unsigned_abs()`
    或 `checked_abs()`

## 练习

1. 写 `fn sum_u8(values: &[u8]) -> Option<u8>`，用 `checked_add` 累加，溢出返回 `None`。
2. 写一个限流器：每秒最多 255 次请求，用 `saturating_add` 计数，并解释为什么不用 `+`。
3. 自己实现 32 位 FNV-1a 校验和，故意把 `wrapping_mul` 改成 `*`，
   分别在 debug 和 `-O` 下运行，记录两种结果并解释。
4. 用 `i64` 分实现购物车总价（数量 × 单价 + 折扣），全部用 `checked_*`，
   最后格式化为"元.分"；再试算一次超过 `i64` 的情形。
5. 解释：为什么 `let x: u8 = 255 + 1;` 是编译错误，而 `let mut y = 255u8; y += 1;`
   在 debug 下 panic、在 release 下回绕？
6. 生成一个含 `NaN`、`-0.0`、`inf` 的 `Vec<f64>`，分别用 `partial_cmp` 和
   `total_cmp` 排序，观察结果差异。
