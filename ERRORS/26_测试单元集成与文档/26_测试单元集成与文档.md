# 第 26 课 · 测试：单元、集成与文档测试

> 所需工具链：rustc 1.85+（edition 2024） ｜ 讲解：本文件 ｜ 独立代码：`26_testing.rs`

## 一、底层原理

### 26.1 测试是可执行的断言

Rust 的测试没有独立框架依赖，`#[test]` 是编译器/标准库直接支持的属性：

```rust
#[test]
fn adds_numbers() {
    assert_eq!(add(2, 3), 5);
}
```

构建测试时，`rustc --test`（或 `cargo test`）会：

1. 生成一个**测试 harness** 的 `main`
2. 收集所有 `#[test]` 函数
3. 逐个（默认并行）调用，捕获 panic，记录成功/失败
4. 打印 `running N tests` / `test result: ok. N passed; ...`
5. 有失败时以非零状态退出

因此：

- 测试函数**不能有参数**（harness 不知道传什么）
- 测试函数返回 `()`，或 `Result<(), E>`（`E: Debug`），后者用 `?` 传播失败
- 测试失败 = 断言 panic 或普通 panic；`#[should_panic]` 反过来期望 panic
- 测试代码放在 `#[cfg(test)]` 模块里，普通构建不会编译它

### 26.2 三层测试

| 层级 | 位置 | 编译单元 | 能访问 | 运行命令 |
|---|---|---|---|---|
| 单元测试 | 源文件内 `#[cfg(test)] mod tests` | 与被测代码同一个 crate | 私有项 | `cargo test --lib` |
| 集成测试 | `tests/*.rs` | 独立 crate | 只有 `pub` API | `cargo test --test name` |
| 文档测试 | `///` 注释里的代码块 | 独立 doctest crate | 文档示例 | `cargo test --doc` |

- **单元测试**用 `use super::*;` 拿到父模块（包括私有函数），适合测内部逻辑
- **集成测试**以"外部使用者"身份链接库，验证公开契约；每个文件是一个 crate
- **文档测试**既是文档又是测试：示例代码必须能编译/运行，防止文档过期

### 26.3 断言与 panic

| 宏 | 失败时 | 要求 |
|---|---|---|
| `assert!(cond)` | panic | `cond: bool` |
| `assert!(cond, "msg {}", value)` | panic，带格式化消息 | `Display` |
| `assert_eq!(a, b)` | panic，打印两边 | `PartialEq + Debug` |
| `assert_ne!(a, b)` | panic，打印两边 | `PartialEq + Debug` |
| `debug_assert!` | 仅 debug 构建 | 同 `assert!` |

- `assert_eq!` 的 `Debug` 要求意味着自定义类型要 `derive(Debug)`
- 浮点不要直接 `assert_eq!`；用误差范围（`(a - b).abs() < EPS`）
- 断言消息写清"期望什么、实际什么"
- `debug_assert!` 只在 debug 构建执行，不能当业务校验

### 26.4 测试组织与运行

```bash
cargo test                       # 跑单元 + 集成 + 文档测试
cargo test adds_numbers          # 名字过滤
cargo test -- --nocapture        # 显示 println! 输出
cargo test -- --test-threads=1   # 串行执行
cargo test -- --ignored          # 只跑 #[ignore] 的测试
cargo test --doc                 # 只跑文档测试
```

- 默认并行执行：共享全局状态（环境变量、文件、端口）会互相干扰，
  用临时目录/随机端口，或 `serial_test` crate
- 测试顺序不保证，不要写"依赖前一个测试"的代码
- 一个测试只验证一个行为；命名用 `行为_条件_期望`
- 失败信息比"通过"更重要：断言消息、`dbg!`、`--nocapture`

### 26.5 `should_panic` 与 `ignore`

```rust
#[test]
#[should_panic(expected = "min must be <= max")]
fn clamp_rejects_bad_bounds() {
    let _ = clamp(1, 10, 0);
}
```

- `#[should_panic]` 要求测试 panic 才算通过
- `expected = "..."` 检查 panic 消息包含子串；不写则"任何 panic"都算通过，
  容易掩盖错误
- `#[ignore]` 默认跳过（如慢测试/需要外部服务）；`--ignored` 才运行

### 26.6 文档测试

````rust
/// 解析端口。
///
/// ```
/// let port: u16 = "8080".parse().expect("valid port");
/// assert_eq!(port, 8080);
/// ```
fn parse_port(text: &str) -> Result<u16, String> { ... }
````

- `cargo test --doc` 会编译并运行这些代码块
- 代码块可加属性：
  - `no_run`：只编译不运行（适合网络/文件）
  - `ignore`：跳过
  - `should_panic`：期望 panic
  - `compile_fail`：期望编译失败（测试文档约束）
- 文档测试让"示例"永远是最新的；库的公开 API 特别值得写
- 二进制 crate 的 doctest 上下文受限，复杂示例可以放到库 crate

### 26.7 单文件项目怎么演示测试

本仓库没有 Cargo 工程，所以示例文件同时包含：

- `main`：正常 `rustc` 编译运行，输出确定性的演示结果
- `#[cfg(test)] mod tests`：`rustc --test` 时编译并由 harness 执行
- `///` 文档测试：`rustdoc --test` 执行

这正是"测试代码与业务代码同文件、`cfg(test)` 隔离"的最小形态。

## 二、具体语法

### 27.1 单元测试模块

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn adds_numbers() {
        assert_eq!(add(2, 3), 5);
    }
}
```

- `#[cfg(test)]` 保证只在测试构建包含
- `use super::*;` 导入被测模块的全部名字（含私有项）
- 测试模块可以嵌套在任意模块里

### 27.2 断言

```rust
assert!(value > 0, "value must be positive, got {value}");
assert_eq!(add(2, 3), 5);
assert_ne!(add(2, 3), 6);
```

- `assert_eq!` 失败时打印 `left`/`right`
- 自定义类型要 `#[derive(Debug, PartialEq)]` 才能用
- 复杂结构用 `assert_eq!(actual, expected)` 对比整个值

### 27.3 `should_panic`

```rust
#[test]
#[should_panic(expected = "out of range")]
fn index_out_of_bounds_panics() {
    let values = [1, 2, 3];
    let _ = values[10];
}
```

- `expected` 是子串匹配，不是完整匹配
- 越具体的消息越好；避免让无关 panic 蒙混过关

### 27.4 返回 `Result` 的测试

```rust
#[test]
fn parse_port_accepts_valid() -> Result<(), String> {
    let port = parse_port("8080")?;
    assert_eq!(port, 8080);
    Ok(())
}
```

- 用 `?` 传播错误，失败时 harness 打印 `Err`
- 返回类型必须是 `Result<(), E>`（`E: Debug`）
- 适合大量"成功路径"断言，少写 `unwrap`

### 27.5 `#[ignore]`

```rust
#[test]
#[ignore]
fn slow_check() {
    // 需要网络/数据库/长耗时
}
```

- 默认跳过；`cargo test -- --ignored` 单独跑
- 用于慢测试、集成环境测试、手动验证

### 27.6 文档测试

````rust
/// Adds two numbers.
///
/// ```
/// assert_eq!(2 + 3, 5);
/// ```
fn add(left: i32, right: i32) -> i32 { left + right }
````

````rust
/// 读取配置（只演示，不真的运行）。
///
/// ```no_run
/// let text = std::fs::read_to_string("app.conf").unwrap();
/// println!("{}", text);
/// ```
fn load() {}
````

### 27.7 集成测试布局

```
my_crate/
├── src/
│   └── lib.rs
└── tests/
    ├── config.rs          # 独立 crate
    └── api.rs
```

```rust
// tests/config.rs
use my_crate::parse_port;   // 只能使用 pub API

#[test]
fn parses_port() {
    assert_eq!(parse_port("8080"), Ok(8080));
}
```

- 每个 `tests/*.rs` 是独立 crate
- 只能访问 `pub` 项；私有逻辑用单元测试
- 集成测试更接近真实调用方，适合验证公开契约

### 27.8 常用命令

```bash
cargo test
cargo test -- --nocapture
cargo test -- --test-threads=1
cargo test -- --ignored
cargo test --doc
cargo test --test config
```

## 三、实际应用与最佳实践

### 28.1 被测函数要"可测"

```rust
fn divide(left: i32, right: i32) -> Result<i32, String> {
    if right == 0 {
        Err(String::from("divide by zero"))
    } else {
        Ok(left / right)
    }
}
```

- 返回 `Result` 而不是 panic，测试可以断言 `Err`
- 纯函数最容易测：输入 → 输出，无全局状态
- 依赖 IO/时间的逻辑抽成 trait，测试时注入假实现（mock）

### 28.2 表驱动测试

```rust
let cases = [(1, 2, 3), (0, 0, 0), (-1, 1, 0)];
for (left, right, expected) in cases {
    assert_eq!(add(left, right), expected);
}
```

- 多组输入共享同一断言，减少样板
- 失败时打印具体 case；复杂场景用 `rstest` crate 的参数化测试

### 28.3 测试套件汇总

```rust
let checks = [
    ("add", add(2, 3) == 5),
    ("clamp_high", clamp(15, 0, 10) == 10),
    ("divide_zero", divide(1, 0).is_err()),
];
let passed = checks.iter().filter(|(_, ok)| *ok).count();
```

示例里用布尔列表做演示；真实项目直接用 `#[test]` 让 harness 收集，
失败会精确定位到函数名。

### 28.4 最佳实践清单

1. **一个测试一个行为**，失败信息能直接定位问题
2. **单元测试放 `#[cfg(test)]`**，集成测试放 `tests/`
3. **公开 API 写集成测试/文档测试**，私有逻辑写单元测试
4. **可失败函数返回 `Result`**，测试里用 `?` 传播
5. **`should_panic` 必须写 `expected`**，避免误判
6. **慢测试 `#[ignore]`**，CI 分层运行
7. **断言消息带实际值**，不要只写 "failed"
8. **避免测试间共享状态**；需要时串行执行或隔离临时目录
9. **浮点用误差范围**，不要直接 `assert_eq!`
10. **用 `--nocapture` 调试**，用 `cargo test` 作为提交前门禁

## 常见陷阱

1. **测试函数带参数**：harness 不会调用；`#[test]` 函数必须无参
2. **忘记 `#[cfg(test)]`**：测试模块进入普通构建，或被当成死代码
3. **集成测试访问私有项**：`tests/` 是独立 crate，只能看 `pub`
4. **测试并行导致共享状态冲突**：环境变量/文件/端口互相干扰；
   `--test-threads=1` 或隔离资源
5. **`assert_eq!` 缺 `Debug`**：自定义类型要 `derive(Debug)`
6. **`should_panic` 不带 `expected`**：任何 panic 都通过，掩盖真实错误
7. **`#[ignore]` 以为默认会跑**：需要 `--ignored`
8. **文档测试没被 `rustc` 编译**：只有 `cargo test`/`rustdoc --test` 会跑
9. **doctest 示例依赖外部环境**：用 `no_run` 或 `ignore` 标注
10. **浮点直接相等**：`0.1 + 0.2 != 0.3`；用误差范围
11. **依赖测试执行顺序**：默认并行且顺序不保证
12. **断言里放副作用**：调试输出被缓冲；用 `--nocapture`
13. **`panic = "abort"` 下 `should_panic` 失效**：测试需要 unwind
14. **测试修改全局状态不恢复**：影响其他测试；用 `serial_test` 或 RAII 守卫
15. **二进制 crate 的 doctest 受限**：把可测逻辑抽到 `lib.rs`
16. **测试名重复/含糊**：失败时难以定位；用 `行为_条件_期望`
17. **只测正常路径**：边界/错误/空输入同样要测
18. **过度 mock**：测的是 mock 不是代码；优先纯函数/集成测试
19. **测试依赖真实网络/数据库**：CI 不稳定；用容器/临时资源
20. **覆盖率当质量**：覆盖不等于断言有效；关注行为而非行数

## 完整示例

见 `26_testing.rs`，按 **① 原理验证 → ② 语法演示 → ③ 应用实战**
三段组织。它同时是一个可运行程序和一组测试：

```bash
# 普通运行（输出与注释逐行一致）
rustc --edition 2024 -D warnings "ERRORS/26_测试单元集成与文档/26_testing.rs" -o run.exe
./run.exe

# 单元测试（#[cfg(test)] mod tests）
rustc --edition 2024 --test "ERRORS/26_测试单元集成与文档/26_testing.rs" -o tests.exe
./tests.exe --test-threads=1

# 文档测试
rustdoc --edition 2024 --test "ERRORS/26_测试单元集成与文档/26_testing.rs"
```

示例共 13 行输出，覆盖：`cfg!(test)`、断言成功/失败、`debug_assert`、表驱动断言、
返回 `Result` 的测试、`should_panic` 消息校验，以及被测函数的实际输出与套件汇总。

实测结果：

- 普通运行：13 行输出与注释预测一致
- `--test`：6 个测试，5 通过、1 忽略（`slow_check`）
- `rustdoc --test`：2 个文档测试全部通过

## 练习

1. 给 `add`/`divide`/`clamp` 写单元测试，覆盖正常、边界、错误三类输入。
2. 用 `#[should_panic(expected = "...")]` 测试 `clamp(1, 10, 0)` 的 panic 消息。
3. 写一个返回 `Result<(), String>` 的测试，用 `?` 传播 `parse_port` 的错误。
4. 用表驱动测试覆盖 `parse_port` 的多个合法/非法输入。
5. 给 `parse_port` 写文档测试；再写一个 `no_run` 的 IO 示例。
6. 设计 `tests/config.rs` 集成测试，只通过 `pub` API 验证配置解析。
7. 把一个慢测试标 `#[ignore]`，分别用默认和 `--ignored` 运行。
8. 解释为什么并行测试下共享全局状态容易 flaky，并给出两种隔离方案。
